# 운영

## 지침 파일

파일마다 원본 하나이고 사본이나 자동 생성본이 없다. 고칠 때는 그 파일만 고친다.

- 루트 `CLAUDE.md`: 공통 규칙.
- 각 업무 폴더의 `CLAUDE.md`: 업무 규칙.
- `.claude/commands/*.md`: 명령어 절차.
- `.claude/skills/*/SKILL.md`: 공통 스킬(LBOX 검색·하이라이트, 법제처 검색, 사업자 확인).
- `공통/브라우저.md`: 브라우저 도구 차이 처리. 실제 브라우저 작업 때만 읽는다.
- `4_서면작성/skills/노동서면작성/`: 공통 서면 문체 원본. 작성 시에만 읽고, 문서 변환 세부사항은 필요한 단계에 읽는다.

모델 이름은 업무 규칙에 고정하지 않는다. 선택한 모델을 사용한다. 자동 API 호출은 이 구성에 포함하지 않는다. 여러 에이전트나 반복 평가도 자동으로 시작하지 않는다.

같은 작업에서 이미 읽은 동일 버전의 규칙을 다시 읽지 않는다. 문서·자료 출력이 잘리지 않도록 범위를 나누고, 읽은 범위는 중복 출력하지 않는다.

## 지침 우선순위와 충돌 정리

사용자의 현재 명시적 지시 → 루트 공통 규칙 → 업무 지침 → 공통 명령어 → 세부 스킬·예시 순서로 적용한다. 제품 자체의 상위 지침·도구 권한은 이 문서로 변경하지 않는다.

- 종결: 루트의 완충 원칙을 적용한다. 과거 서면의 단정형 예시는 참고이고 자동 예외가 아니다.
- `/서면`: 프레임이 있으면 DOCX까지 생성한다. 사용자가 텍스트만 지정하면 그 지정을 따른다. 서면 종류는 프레임 표지가 정하고, 노동위 기록 추출과 반박 구성은 자료에 따라 켜는 갈래이다.
- 보완 메모: MD 하단에 모으고 제출용 DOCX 본문에는 넣지 않는다. 빈 목차는 유지하되 없는 사실을 채우지 않는다.
- 증거 발췌: 같은 호증이라도 다른 대목이면 여러 번 넣을 수 있다. 동일 대목의 중복 삽입은 피한다.
- 프레임·담당자 수정본이 있으면 이를 기준으로 부분 수정한다. MD가 최신이라고 가정해 DOCX를 재병합하지 않는다.
- 사건상태가 검증되어 있으면 `공통/사건상태.md`의 변경분 읽기를 적용한다. 검색의 필수 범위와 인용 원문 검증은 줄이지 않는다.

## 검사

루트에서 Python으로 실행한다. 녹취는 기존 `녹취.ps1`이 선택한 환경을 사용한다.

PDF 추출에는 `pypdf`가 필요하며, 미설치 시 명시적 오류를 반환한다.

스크립트가 파이썬 모듈이 없다고 멈추면(`ModuleNotFoundError`) 사용자에게 설치를 맡기지 않고 AI 가 그 폴더의 `requirements.txt` 로
설치한 뒤 다시 돌린다(`python -m pip install -r 4_서면작성/requirements.txt`, 엔진은 `6_손해배상계산/requirements.txt`).

```powershell
python 공통/scripts/system.py check
python 공통/scripts/system.py budget
python -B 공통/scripts/dashboard.py --open
python -B -m unittest discover -s 공통/tests -v
```

`-B` 는 `__pycache__` 를 만들지 않게 한다. 이 폴더는 OneDrive가 동기화하므로 재생성되는 캐시를 남기지 않는다.

`budget`은 명령어별 지침 분량과 중복·고아 지침을 보고한다. 글자 수를 토큰 수로 바꾸어 적지 않는다.

**분량에 상한을 두지 않는다.** 지침이 길어서 문제인 경우는 없다. 문제가 되는 것은 쓸모없는 지침이지 분량이 아니므로, 이 수치를 근거로 지침을 줄이지 않는다. 결과물의 완성도를 높이는 지침은 분량과 무관하게 남긴다. `budget`이 실패로 처리하는 것은 지침 파일이 아예 없는 경우뿐이다.

수치를 보는 목적은 셋이다. `changed_since_record`로 **무엇이 언제 늘었는지** 확인하고(`--record`로 지금 분량을 기준선에 적는다), `duplicated`로 **같은 규칙이 두 곳에 적혀 갈릴 자리**를 찾고, `orphans`로 **어느 명령어도 읽지 않는 지침**을 찾는다. 중복은 파일 수가 적은 것부터 나오며, 여러 파일에 두루 나오는 문장은 대개 모든 명령어에 붙이는 정형 안내이다. 줄일지 여부는 그 문장을 열어 보고 사람이 정한다.

사건 자료와 인용 원문을 읽는 범위는 이 수치와 무관하게 줄이지 않는다.

`dashboard`는 사건 폴더를 훑어 `공통/캐시/현황.html` 을 만든다. 라운드·최근 활동·미해결 표시와 `style_check`·`citation_check` 결과를 한 표에 모은다. 아무것도 고치지 않고 새로 입력할 자료도 없다. 표의 '다음 할 일'은 폴더 상태에서 짐작한 것이므로 근거로 삼지 않고 사건을 열어 보고 정한다.

`check`는 필수 지침과 명령어가 있는지, 스킬 머리말(`name`·`description`)이 바른지 본다. 스킬 폴더 이름과 `name`이 다르면 Claude가 그 스킬을 찾지 못한다.

## 시스템 파일 올리기

사람은 git 을 치지 않는다. 작업을 맡은 AI 가 두 때에 확인해 올린다.

- **작업을 시작할 때** — 다른 PC나 사람이 고쳐 두고 올리지 않은 시스템 파일이 있으면 먼저 올리고 시작한다.
- **시스템 파일을 고친 작업을 마칠 때** — 고친 것을 올린다.

PC에서는 아래 순서로 한다. 작업본은 OneDrive 가 두 PC에 맞춰 두고 `.git` 은 PC마다 따로이므로, 먼저 원격을 받는다.
`receive.py` 가 이 PC의 이력을 원격에 맞추고(`reset --mixed`), 클라우드 세션(claude.ai/code)에서 고쳐 main 에 머지한 것처럼
OneDrive 에 없는 원격 변경을 작업본으로 받는다. 받는 것은 작업본 파일이 예전 커밋 판 그대로인 경우뿐이고, 이 PC에서 고친
파일과 사건 자료는 건드리지 않는다. 이 단계를 건너뛰면 작업본의 옛 판이 이 PC의 변경으로 잡혀, 올릴 때 원격의 고침을 되돌린다.

```
python -B 공통/scripts/receive.py
공통/scripts/g.bat status --short --untracked-files=all
```

`receive.py` 가 '충돌'(종료 코드 2)을 내면 원격도 고치고 이 PC에서도 고친 파일이다. 그 파일은 올리지 않고 사용자에게 확인한다.

새 작업(세션)을 열면 `.claude/settings.json` 의 시작 훅이 `receive.py --auto` 를 먼저 돌려 원격 변경을 받는다. 받은 것이 있으면
그 결과가 작업 첫머리에 나오므로, 받은 개수와 충돌만 사용자에게 한 줄로 알린다. 올리기 전에는 위 순서를 그대로 한다.

남은 것이 없으면 끝이다. 남은 것이 있으면 **올리기 전에 새 파일(`??`)을 하나씩 본다.** `.gitignore` 는 이름과 위치로만 거르므로 `사건/` 밖에 생긴 사건 자료는 걸러지지 않을 수 있다(예: 루트에 생긴 증거 첫 면 모음 이미지, 녹음파일 옆에 생긴 간이 전사본 `.녹취.txt`·`.녹취.json`, 사건 폴더 밖에 저장한 계산표). `--untracked-files=all` 은 새 폴더를 `?? 폴더/` 한 줄로 묶지 않고 파일마다 보여 준다.

새 파일이 모두 시스템 파일(지침·명령어·스킬·스크립트·엔진·테스트·양식)이면 올린다.

```
공통/scripts/g.bat add -A
공통/scripts/g.bat commit -m "무엇을 고쳤는지"
공통/scripts/g.bat push -q origin HEAD:main
```

사건 자료로 보이는 것(의뢰인 문서·증거 이미지·녹취·전사본·계산 결과)이 하나라도 있으면 `add -A` 를 쓰지 않는다. 그 파일은 올리지 않고 경로를 사용자에게 알린다(사건 자료는 각 폴더의 `사건/` 아래에 둔다). 어느 쪽인지 애매한 파일도 올리지 않고 묻는다. 시스템 파일만 아래처럼 담은 뒤 위와 같이 commit·push 한다.

```
공통/scripts/g.bat add -u
공통/scripts/g.bat add -- "새 시스템 파일 경로"
```

`add -u` 는 이미 추적하는 파일의 고침·지움만 담고 새 파일은 담지 않는다.

- 목록에 **지움(`D`)이 있거나 누가 왜 고쳤는지 모르는 변경**이 있으면 OneDrive 동기화가 덜 끝났을 수 있다. 그대로 올리면 다른 PC에서 올린 것을 되돌린다. 올리기 전에 사용자에게 한 줄로 확인한다.
- 이번 작업에서 `공통/판례기록/` 에 적은 줄에 사람 이름·소속·병명이나 의뢰인·상대방의 내부 규정, 서면 전략이 들어가지 않았는지 본다. 들어갔으면 `공통/판례기록/README.md` '적지 않는 것'대로 고친 뒤 올린다. 이 폴더는 시스템 파일로 GitHub 에 올라간다.
- 엔진(`6_손해배상계산/engine`·`tests`)을 고쳤으면 `6_손해배상계산` 에서 `python -B -m pytest tests -q -p no:cacheprovider` 를, 공통 스크립트(`공통/scripts`)나 서면 스크립트(`4_서면작성/scripts`)를 고쳤으면 위 '검사'의 `공통/tests` 시험을 실패 없이 통과시킨 뒤 올린다.
- `.bat` 을 고쳤으면 원래 인코딩과 CRLF 가 그대로인지 바이트로 본다. 이 저장소의 `.bat` 은 CP949 인 것과 UTF-8(`chcp 65001`) 인 것이 섞여 있고, 편집 도구는 UTF-8 로 저장하므로 CP949 파일은 파이썬으로 `cp949` 로 읽고 쓴다. 인코딩이 바뀌면 한글 파일명이 깨져 Windows 콘솔에서만 실행이 멈추고, 리눅스·클라우드 검사로는 드러나지 않는다.
- 저장소가 없거나(`g.bat` 이 `Repository not found` 를, `receive.py` 가 '건너뜁니다'를 낸다) 원격에 연결되지 않으면 건너뛰고 본 작업을 한다. **git 때문에 사건 작업을 멈추지 않는다.**
- 클라우드 세션(claude.ai/code)은 그 세션의 브랜치·PR 규칙을 따른다.

## 탐색과 출력

폴더를 훑을 때 `사건`·`백업`·`캐시`·`__pycache__`를 제외한다. 사건 자료는 `scan`으로 확인하고 전체 목록을 나열하지 않는다.

다만 판례를 검색할 때에는 `공통/캐시/판례검색기록/`과 `공통/캐시/법제처/`의 **파일·폴더 이름**을 먼저 훑어 같은 쟁점을 다룬 기록이 있는지 본다(`lbox-검색` 7항). 내용까지 읽는 것은 이름이 걸리는 것만으로 한다.

Windows 긴 경로는 셸 `find`가 열지 못하고 실패 목록만 길게 남기므로, 경로 탐색은 파이썬이나 `system.py`로 한다. 실패한 탐색의 오류 목록을 그대로 읽어 들이지 않는다.

출력이 길어질 것으로 예상되는 명령은 결과를 파일로 저장하고 필요한 범위만 확인한다. 이는 도구 출력에만 적용하고, 사건 자료와 인용 원문을 확인하는 범위는 줄이지 않는다.

## 작업 보고

- 사용자에게 하는 답변과 보고는 모두 한국어로 쓴다.
- 작업을 마치면 **소요시간**을 밝힌다. 요청을 받은 시각에 `Get-Date`로 시작 시각을 기록해 두고, 마칠 때 다시 확인하여 `소요시간 36분(0.6시간)`과 같이 분과 시간(소수 첫째 자리)을 함께 적는다. 시각을 기록하지 못했으면 파일 생성 시각 등으로 추정하고 추정치임을 밝힌다.

## 검증 범위

공통 스크립트 검사는 경로·지침 파일·입력 변경·추출 캐시를 확인한다. LBOX 로그인·검색·하이라이트, Word 전체 렌더, 음성 인식 정확도, 계산 엔진의 법적 정확성을 대신 검증하지 않는다. 실제 사건 작업에서 해당 검증을 수행하고 성공과 미확인을 구별해 보고한다.

**판례 검색 방법을 바꾸면 찾는 힘을 다시 잰다.** 검색어 규칙, `lawgo.py`의 수확·인용 순위, LBOX 수확기를 고치기 전과 뒤에 `python -B 공통/scripts/search_eval.py run`을 돌려 출력의 `기준`보다 떨어지지 않았는지 본다. 법제처 API만 쓰고 LBOX에는 요청을 보내지 않는다. 절차·기준 결과와 LBOX 하급심 시험은 `공통/검증/판례검색/README.md`에 있다.

**Word COM(`Word.Application`)으로 문서를 검증·변환할 때는 사용자가 같은 PC에서 Word를 쓰고 있을 수 있다고 전제한다.** 사용자가 탐색기에서 연 문서가 자동화 중인 숨은 Word에 붙을 수 있고, `DisplayAlerts = 0` 상태에서 그 Word를 종료하면 사용자 문서가 저장 확인 없이 닫힐 수 있다(2026. 9. 17. 황도윤 징계 사건 DOCX 검증 중 실제로 발생: 사용자가 연 다른 문서가 붙어 스크립트가 멈추었고, `finally`에 `Quit`이 있었다).

- 렌더 검증은 LibreOffice(`soffice --headless --convert-to pdf`)로 먼저 하고, Word는 열리는지 확인하는 정도로 줄인다. 다만 LibreOffice는 한글 줄바꿈이 달라 면수가 Word보다 적게 나올 수 있으므로, 면수를 맞출 때는 Word로 확인한다.
- Word는 필요한 동안만 띄우고, 문서는 읽기 전용으로 연다.
- 자기가 연 문서를 닫은 뒤 `$word.Documents.Count`가 0일 때만 `Quit`한다. `finally` 블록에서도 같다. 다른 문서가 남아 있으면 종료하지 않는다. PowerShell에서는 `$word.Quit([ref]0)`처럼 `[ref]`로 넘긴다. `$word.Quit(0)`은 실패하여 Word 프로세스가 남는다.
- 스크립트가 멈추면 Word 프로세스를 강제 종료하지 않는다. 창 제목과 문서 목록으로 사용자 문서가 붙었는지 먼저 확인하고, 자기가 연 문서만 닫는다.
